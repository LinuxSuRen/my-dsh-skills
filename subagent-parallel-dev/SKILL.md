# 多子代理并行研发编排

## 1. 契约先行（并行的前提）

- 动手前把**跨仓库协议**写成一份设计文档（消息流/entry 编码/字段/错误码/端点契约），作为所有子代理的**唯一事实源**；文档放主仓库，其它仓库的子代理按路径读取。
- 子代理 prompt 必须自包含：worktree 路径、必读清单（设计文档具体章节 + 目标仓库的 AGENTS.md/README/既有范式文件）、交付物清单、验证命令、**禁止 commit/push**、报告格式（文件清单/测试结果/与设计偏差）。
- 分仓认领，一人一仓一 worktree，统一分支名（跨仓库一致便于批量管理）；worktree 从最新 `origin/master` 创建。

## 2. 早期契约审查（落盘即审，不等交付）

- 子代理开始落盘后，**协议关键文件一出现就读**（消息结构体/编解码层/报文组装），对照设计逐字段核：一旦发现漂移立即 `send_message` 批回修正——修复成本在落盘期最低。
- 双向核对：UI 的 API 层字段 vs 后端响应结构；服务端 entry 编码 vs 平台解析路径；跨服务同名约定（如时间戳格式、错误码大小写）必须三端比对。
- 容错点前置声明：允许的输入差异（如 ts 多格式、可选字段缺失）在消费者侧显式兼容，而不是要求所有生产者严格一致。

## 3. 独立复测纪律（不信任，要验证）

- 子代理报告的"测试通过"**必须由主 agent 实跑复核**（同命令再执行一次）。
- "既有失败"申报必须对照证实：`git stash` 后在干净树复跑，或用**纯净 master 临时 worktree** 复现（后者还能顺带发现 master 上的存量阻塞——本次实战曾借此发现 sed 破坏 protobuf rawDesc 导致全量测试 panic 的基线 bug 并顺手修复）。
- 真实服务 E2E 兜底：单元测试对跨仓库集成无能为力。起真实中间件（Docker Redis）+ 真实子进程服务 + 平台真实模块跑全链路，`integration` build tag 隔离入库可复跑——本次抓出 3 个单测发现不了的 bug（回执缺失、权限契约不匹配、重复签发令牌）。

## 4. 推进节奏与安全

- 主 agent 只做：worktree/分支创建、契约管理与增量批注、审查、复测、提交；实现全部下沉子代理；主 agent 可认领无人覆盖的接缝件（如本例的 video 路由接缝）。
- 提交需用户明确授权；有进展才 commit+push（每仓库一次成型提交 + 后续增量修复提交），身份用研发本人（git-identity）。
- 子代理空转 2~3 轮无落盘时发优先级指引并要求遇阻塞显式上报；文件分钟级 mtime 是最廉价的活性探针。
- 修复链上新 bug（如改 A 引入编译错）要立即补提交修复，不留坏分支。
