# 长期运行磁盘容量守卫

核心原则：**"磁盘会被写满"是确定性事件，不是意外**。任何 7x24 运行的写入者，容量治理必须发生在设计期，而不是等运维半夜救火。长期无人值守的边缘设备尤其如此——没有人在现场清磁盘。

## 1. 写入者盘点与上限（新组件上线前）

逐项回答"它写什么、写多快、谁负责删、删不掉怎么办"，任何一项答不上来就是缺口：

| 写入者 | 必须有的上限机制 |
|---|---|
| 服务日志 | 分级限速 + logrotate（rotate 数量有上限）或结构化日志按天/大小分段 |
| 录像/媒体分段 | 滚动窗口：按容量或按时长保留，先落盘后补传的队列要双重限额 |
| 磁盘队列 | 目录级配额 + 入队前检查 + 超限拒绝/淘汰（见 edge-offline-pipeline-dev 的双重磁盘限额） |
| 缓存目录 | LRU/容量上限，启动时与周期性清理 |
| 数据库 | WAL checkpoint、归档清理、表空间预算 |
| 导出/上传产物 | 临时文件带 TTL 清理；失败产物进死信目录并限额 |
| core dump | `ulimit -c` 限制 + 固定目录配额（见 §4） |

- 写入速率要可估算：`日增量 = 速率 × 时间`，对照保留期得出稳态占用，写进部署文档。

## 2. 磁盘预算与水位线

- **预算制**：多写入者共享磁盘时按目录分配预算（绝对值或百分比），**各预算之和 ≤ 磁盘容量 80%**，剩余是系统、DB、临时文件的 headroom——不允许任何写入者"用到写满为止"。
- 水位判断优先用**配额目录的实际占用**（du），而非整盘使用率——预算内自治，不互相误伤。
- 三档水位动作（阈值按业务调，示例 70/85/95）：

| 水位 | 动作 |
|---|---|
| 低（~70%） | 告警（指标进 observability-design 的监控面），可行动的告警 |
| 中（~85%） | 启动/加速淘汰最旧数据；新任务背压拒绝（队列入队返回"磁盘紧张"而非无限堆积） |
| 高（~95%） | 降级：停写非关键数据（debug 日志、录像降帧）、只保留最小审计日志，触发保护动作并上报 |

- 根分区/系统盘不放电位型数据（录像、队列、导出产物）；能单独挂盘就单独挂。

## 3. 淘汰与清理的工程纪律

- **清理必须崩溃安全**：先 rename 到待删目录再删（原子状态机，参照 edge-offline-pipeline-dev），删一半崩溃不破坏有效数据。
- **删除失败不能阻塞主流程**：清理是后台任务，失败记日志、下轮重试，不允许因清理失败导致写入路径报错。
- **两个时机都要清**：启动时（清上次异常遗留）+ 运行中周期清（水位触发或定时）；只在启动清一次的组件必然在长期运行后堆积。
- 淘汰顺序明确：最旧优先（FIFO）或按业务价值（先丢低价值数据），写死在代码里，不靠人判断。

## 4. 常见堆积源速查（排查先看这些）

| 堆积源 | 陷阱 | 治理 |
|---|---|---|
| 容器 json-file 日志 | 默认**无限增长** | 日志驱动配 `max-size` + `max-file` |
| journald 持久化 | `/var/log/journal` 无限额 | `SystemMaxUse=` 配额 |
| logrotate | 配了 rotate 但压缩文件堆积/份数无上限 | `rotate N` + `maxsize`，验证实际生效 |
| core dump | 崩溃循环时瞬间写满 | `kernel.core_pattern` 固定目录 + 配额/关闭 |
| `/tmp` | 被当持久目录用；tmpfs 填的是内存 | 业务数据不进 /tmp；tmpfs 设 size 上限 |
| SQLite WAL | checkpoint 不跑则 `.wal` 无限涨 | 定期 checkpoint；监控 WAL 大小 |
| Docker 镜像/容器垃圾 | 构建机器尤其严重 | 定期 `docker system prune` 策略 |
| 截图/快照类调试产物 | 循环里每帧落盘 | 上限 + 覆盖写，或禁用后清理遗留 |

## 5. 排查手册（磁盘已满时）

按顺序执行，先定位后删除：

1. `df -h` 看哪个挂载点满；**同时 `df -i`**——inode 满而空间未满是经典陷阱（海量小文件：队列、session、分片），症状是 `No space left on device` 但 df -h 有余量。
2. `du -xh --max-depth=2 <挂载点> 2>/dev/null | sort -rh | head` 逐层下钻定位大目录；容器环境先看 `/var/lib/docker`。
3. **删了文件空间不释放**：`lsof +L1` 找已删除但仍被进程持有句柄的大文件——重启持有进程或让其重开日志句柄才真正释放；这是"日志已删但磁盘还满"的头号原因。
4. 清理动作守规：先砍有淘汰机制数据的旧段（录像、队列），再砍日志；**不动业务数据库与用户数据**；删除前确认配额归属。
5. 恢复后补水位监控与告警——同样的满盘不允许发生第二次。

## 6. 检查清单（设计期过一遍）

1. 本组件写磁盘的每个路径都有上限与淘汰机制？
2. 预算之和 ≤ 80%，水位三档动作已实现？
3. 清理崩溃安全、失败不阻塞、启动+周期双时机？
4. 部署文档写明日增量与稳态占用估算？
5. 磁盘使用率与增长速率已进监控，告警可行动？
6. 容器/journald/core dump 等系统级堆积源已按 §4 配置？
