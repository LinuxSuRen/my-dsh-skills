# 多方案竞速验证（高不确定需求）

核心原则：**高不确定时，用并行实证代替串行猜测**。方案没把握一次选对，与其开会争论或拍脑袋"方案先行"，不如让 2~3 个候选方案在各自 worktree 里同时落地、跑同一份自动化 E2E 判据，让数据说话。竞速的价值一半在选出赢家，一半在**快速证伪**——被数据淘汰的方案附带的结论，是最值钱的经验。

## 1. 启用门槛（三个条件缺一不可）

- **不确定性够高**：关键技术路径有 2~3 个候选各有未知数（如导航算法：图优化 vs 采样式 vs 端到端；新协议逆向、性能优化路径不明）；常规需求、方案已明确 → 不启用，按 arch-dev-workflow 最小实现走单方案，竞速是资源浪费。
- **判据可自动化**：能写出客观、可自动执行的 E2E 验收（成功率、误差指标、时延、资源占用、跑分）。**判据无法自动化时先解决判据，再谈竞速**——人肉主观打分的"竞速"必退化成各说各话。
- **资源足够**：N 个方案 = N 份 worktree + N 倍构建/测试开销。动手前估算磁盘、CPU 核数、内存、GPU/外设；不够就砍方案数或串行分批（先粗筛后全量）。

同时设定**时间盒与轮次上限**（如"3 轮跑分或 2 天，到点强制收敛"），防止探索无限发散。

## 2. 布局

- 一个方案一个 worktree 一个分支：`explore/<需求标识>-a|b|c`；从同一主干基点创建，保证可比。
- **判据同源**：E2E 测试/跑分脚本放在各分支同一路径（或独立 bench 仓库），内容一致——判据不同源的跑分没有可比性。
- 每个方案在分支内写一行**可证伪的假设**（"本方案赌 X 成立"），赌注要落在关键决策点（算法/架构/依赖）上，不在无关细节上开分支。
- 数据集/测试场景固定版本、固定随机种子；环境差异是跑分噪声的头号来源。

## 3. 并发执行

- 各 worktree 独立构建→测试→跑分，天然互不污染；**共享资源显式错峰**：端口、GPU、外设、数据库会跨 worktree 冲突，用端口偏移、容器隔离或错峰调度。
- AI 协作模式：每条 explore 分支交一个子代理独立实现与自测（prompt 自包含：worktree 路径、假设、判据、验证命令、禁止 commit），主代理只管判据与记分——编排纪律见 subagent-parallel-dev；主代理对子代理自报的结果必须实跑复核。
- 结果落盘成表：每轮记录（方案、轮次、指标、环境、变体说明），多轮看均值与分位数，单轮胜负当噪声处理。

## 4. 经验积累与收敛

- **证伪即淘汰**：假设被数据打脸的分支立即出局，不恋战（沉没成本不是理由）；淘汰时留一行结论："X 方案因 Y 被证伪"。
- 允许树状派生：优势方案分支上开新 explore 分支试变体，但**活跃分支数守住上限（3~5）**，超出先淘汰再开新。
- 收敛条件：某方案在判据上**多轮稳定占优**（非单次噪声）→ 定为基准方案。
- 落选结论集中汇总成对比表——这正是 skill-distillation 的最佳素材（踩坑根因、方案取舍原因）。

## 5. 收尾

- 胜出方案转正：清理探索性改动，rebase 到最新主干，走正常 PR 流程（branching-workflow）。
- 删除全部 explore worktree 与分支（arch-dev-workflow 的 worktree 纪律），不留"以防万一"的分支。
- PR/设计文档里写清：候选方案、判据数据、落选原因——半年后没人敢动这段代码时，这份对比就是意图债的偿还。

## 6. 检查清单

1. 三个启用条件（不确定、判据自动化、资源）都满足？
2. 时间盒/轮次上限已设？
3. 判据各分支同源、数据与种子固定？
4. 每方案一行可证伪假设，证伪即淘汰？
5. 共享资源（端口/GPU/外设）无跨 worktree 冲突？
6. 落选方案都留了证伪结论？
7. 胜出方案走 PR，explore 分支与 worktree 清零？

## 与既有技能的关系

- **subagent-parallel-dev**：本技能管"方案未定的竞速阶段"；定案后需要跨仓库/多单元并行实施时，交给 subagent-parallel-dev。
- **arch-dev-workflow 方案先行**：高不确定场景下竞速是"方案先行"的实证前置——用数据代替争论得出方案，再向研发确认；资源不足或低不确定时仍直接最小实现。
- **skill-distillation**：竞速产出的证伪结论与取舍数据是首选沉淀素材。
